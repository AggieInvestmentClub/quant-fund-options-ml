# Server calculator and storage benchmarks — October 28, 2026

These measurements were made on `darkpool` (Ubuntu 26.04, Python 3.14.4,
16 logical CPUs, 30 GiB RAM) with one worker. OPRA flatfiles and stock histories
were read from the rotational `/srv/data` RAID1 volume. Benchmark outputs were
written to isolated scratch directories. No production outputs were replaced.
The raw logs remain under `/home/aarya_options/quant-bench-results/` on the server.

## 1. Reusing the IV price bracket and adding the C++ CRR kernel

The first change reuses the two endpoint price residuals already calculated by
`compute_row_iv_task()`. It avoids two repeated CRR price calls in `compute_iv()`;
it does not change the tree depth. The second change moves each CRR tree's
backward induction into C++.

The same April 21, 2026 OPRA file contained 335,276 raw rows. With
`--underlyings AAPL`, the pipeline selected 245 eligible contracts and wrote
242 IV rows. Each version used the same local stock history, DGS3MO rate file,
one worker, and fresh output paths. The three trials were interleaved. All 13
output CSVs matched the original within `1e-8`.

| Version | Commit | Wall seconds, three trials | Mean wall seconds |
| --- | --- | --- | ---: |
| Original Python | `a621095` | 21.82, 19.39, 21.10 | 20.77 |
| Reused IV bracket | `a9c6de9` | 20.22, 20.03, 18.97 | 19.74 |
| Reused bracket + C++ CRR | `5f56883` | 2.75, 2.54, 2.52 | 2.60 |

Bracket reuse saved about 5.0% of end-to-end wall time on this slice. C++ was
about 7.6 times faster than bracket reuse alone, and about 8.0 times faster
than the original, for the same slice.

A separate fixed 160-contract, pricing-only fixture gave 11.53, 11.46, and
11.20 seconds for the original versus 10.62, 10.94, and 10.75 seconds for
bracket reuse. Both matched the saved IV and Greek reference. The respective
means were 11.40 and 10.77 seconds, a 5.5% improvement. This fixture excludes
OPRA parsing and CSV output.

## 2. Testing hard disk versus RAM

Five April 20–24 OPRA files contained 1,685,477 raw rows. The C++ branch
processed AAPL with one worker and wrote 1,117 contract rows. The OPRA inputs
were either the original `/srv/data` files or identical files copied into
`/dev/shm`; outputs went to the SSD home volume or `/dev/shm`. The stock and
rate inputs stayed on `/srv/data` in every run. All 21 output CSVs matched.

| OPRA input | Output | Wall seconds, two trials | Mean seconds |
| --- | --- | --- | ---: |
| Hard disk | SSD | 12.63, 12.25 | 12.44 |
| Hard disk | RAM | 11.93, 12.80 | 12.37 |
| RAM | SSD | 12.60, 12.59 | 12.60 |
| RAM | RAM | 12.94, 12.72 | 12.83 |

Moving these inputs and outputs to RAM did not improve this workload. A
separate warm-cache read and parse test recorded zero physical-read bytes.
A targeted cold-read check used `posix_fadvise(DONTNEED)` on those five OPRA
files and then read 19.8 MB from the rotational volume. Gzip reading and CSV
decoding took 1.02 seconds cold versus about 0.71 seconds warm; the existing
row-by-row ticker parser took about 8.0 seconds on the same rows. The cold-read
check did not evict stock-history files, so it is not a full cold-cache run.

## 3. Removing the measured parsing cost

The new `parse_opra_option_tickers()` extracts ticker fields and parses expiry
dates in vectorized Pandas operations. It leaves pricing, filtering, and Greek
formulas unchanged. Its fields matched the old parser for all 1,685,477 raw
rows in the five files; a separate regression covers invalid tickers. On the
five-day AAPL run, three trials took 5.86, 5.47, and 5.52 seconds (mean 5.62),
compared with 12.44 seconds for the previous C++ branch with disk input and SSD output.
All 21 generated CSVs matched within `1e-8`.

For a larger test, one unfiltered April 21 run selected 78,577 eligible
contracts across 3,509 symbols and wrote 29,872 IV rows. With disk input and
disk scratch output, the previous C++ branch took 43.53 seconds and the new
parser took 40.92 seconds. With the new parser, disk input and RAM output took
40.42 seconds; RAM input and output took 42.03 seconds. All 13 generated CSVs
matched within `1e-8`. These full-universe timings are single trials, so
subsecond differences between storage locations are not conclusive.

The practical next step is to keep the vectorized parser and measure the
owner's actual historical date range. A larger or cold-cache run may have a
different I/O share, especially when stock-history reads and output volume
grow. These tests do not establish the runtime of the owner's full run.
